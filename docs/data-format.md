# Data format (`.lnb`)

The translations are stored as binary resources named `language.{locale}.{type}.lnb`, one file per locale and type:

| Type | Content | Example key → value |
| --- | --- | --- |
| `languages` | names of languages | `cs` → `Czech` |
| `territories` | names of countries and regions | `DE` → `Germany` |
| `currencies` | names and symbols of currencies | `CZK` → `česká koruna`, `CZK-count-few` → `české koruny` |

`{locale}` uses an underscore instead of a dash (`en_GB`, `sr_Latn_RS`). Every file is complete and stands on its own: `en_GB` does not refer to `en`, and a locale is never assembled from several files.

The format is read and written by hand (`LocaleNames.Utils.LocaleResourceFormat`), with no reflection and no serializer, so it is safe for trimming and native AOT. The data files are generated by the `PrepareLocaleData` tool from [Unicode CLDR](https://github.com/unicode-org/cldr-json).

## Layout

A file is a 3 byte header followed by a deflate-compressed payload:

```
offset  size  content
0       1     'L' (0x4C)   ┐ magic, identifies the file
1       1     'N' (0x4E)   ┘
2       1     version      currently 1
3       ...   deflate stream (RFC 1951, raw: no zlib or gzip header, no checksum)
```

The decompressed payload is a list of key/value pairs:

```
payload = count entry*count
entry   = key value
key     = string
value   = string
string  = length bytes
count   = varint
length  = varint (number of bytes, not characters)
bytes   = UTF-8, no terminator, no byte order mark
```

There is nothing else in the payload: no padding, no trailing data.

### varint

An unsigned integer, 7 bits per byte, least significant group first (LEB128). The high bit of a byte says whether another byte follows.

| Value | Bytes |
| --- | --- |
| 0 | `00` |
| 6 | `06` |
| 127 | `7F` |
| 128 | `80 01` |
| 300 | `AC 02` |

Only values up to `int.MaxValue` are valid (at most 5 bytes).

### Order

The order of the entries is part of the data. It is the order of the dictionary the file is read into, and lookups by a name (`FindCountryCode`, `FindLanguageCode`, `FindCurrencyCode`) return the first match, which matters when two codes share a name. The writer keeps the order of the dictionary it is given. If a key repeats, the later entry wins.

## Example

The dictionary

```
CZ → Česko
DE → Německo
```

has this payload (23 bytes):

```
02                            count = 2

02  43 5A                     key    length 2  "CZ"
06  C4 8C 65 73 6B 6F         value  length 6  "Česko"      (Č is two bytes in UTF-8)

02  44 45                     key    length 2  "DE"
08  4E C4 9B 6D 65 63 6B 6F   value  length 8  "Německo"    (ě is two bytes in UTF-8)
```

and the whole file is (28 bytes, the last 25 are the deflate stream):

```
4C 4E 01  63 62 72 8E 62 3B D2 93 5A 9C 9D CF E4 E2 CA E1 77 64 76 6E 6A 72 76 3E 00
```

Compression does not pay off for such a tiny file; the real ones are much larger and repetitive (`cs.territories` has 310 entries and takes 2.9 kB, `cs.currencies` 1639 entries and 14 kB). The whole data set is about 8.7 MB for 2165 files.

## Reading

```
1. read 3 bytes                  not 'L' 'N', or version != 1  → InvalidDataException
2. inflate the rest of the stream
3. count = varint
4. repeat count times:
       key   = string
       value = string
       dictionary[key] = value
5. anything left in the payload   → InvalidDataException
```

The reader checks every length against the data that is left (a count of entries needs at least two bytes each), so a corrupt or malicious file ends with `InvalidDataException` and never with a huge allocation. The deflate stream carries no checksum; the resources are part of an assembly, whose integrity is a matter of its signature.

## Compatibility

Every reader accepts exactly the version in the header and rejects others. A change of the layout needs a new version number, and `LocaleResourceFormat` can then read both, since the resources of an older `LocaleNames.Data` may meet a newer `LocaleNames.Core`.

## Viewing a file

`samples/LocaleNames.Viewer` is a small cross-platform (Avalonia) desktop app that opens an `.lnb` file and lists its entries in their stored order, with a filter by code or translation. Open a file with the button, drop it on the window, or pass it on the command line:

```bash
dotnet run --project samples/LocaleNames.Viewer -- src/LocaleNames.Data/Resources/language.cs.territories.lnb
```

## Regenerating the data

Run `PrepareLocaleData`. It downloads the CLDR release configured in `Program.cs`, flattens the currencies into the key scheme above, and rewrites `src/LocaleNames.Data/Resources/*.lnb`. The currency keys are the code (`CZK`) for the name, `CZK-count-few` and the other plural categories for the plural names, and `CZK-symbol`, `CZK-symbol-alt-narrow` and the like for the symbols.
